# Проект структуры JSON для поверхностей и технических требований

Статус: предложение для обсуждения от 8 октября 2026 года. Утверждены формат JSON с JSON Schema, требование описывать все поверхности с относящимися к ним техническими требованиями и передача общей информации чертежа отдельным блоком, обязательным для учёта при построении. Ниже предложены конкретные поля и правила будущего контракта; исполняемая JSON Schema ещё не создана.

Первый агент должен передать достаточно сведений для восстановления номинальной геометрии детали и сохранить требования к её изготовлению. Если чертёж не позволяет однозначно восстановить форму, результат должен явно показывать недостающие сведения.

## Общая структура

| Поле | Содержание |
| --- | --- |
| `schema_version` | Версия контракта между агентами. |
| `drawing_general` | Отдельный блок общей информации о чертеже и детали: исходный документ, единицы, материал, нормативные документы, общие требования и примечания. Обязателен для учёта агентом построения. |
| `coordinate_systems` | Начало координат, направления осей, ориентация систем и преобразования между ними. Выбранная агентом система помечается как принятое соглашение. |
| `views` | Виды, разрезы и сечения, страницы и области PDF, направления проецирования и связи между изображениями. |
| `bodies` | Тела детали и их оболочки, включая границы внутренних полостей. |
| `surfaces` | Полный перечень ограниченных поверхностей детали с уникальными идентификаторами. |
| `topology` | Общие рёбра, вершины, контуры и их ориентированное включение в поверхности и оболочки. |
| `features` | Отверстия, пазы, резьбы и другие конструктивные элементы, объединяющие относящиеся к ним поверхности. |
| `dimensions` | Номинальные размеры, измеряемые элементы, направления измерения и ссылки на размерные допуски. |
| `datums` | Базовые элементы, обозначения баз и связи с поверхностями; для системы баз сохраняется порядок. |
| `requirements` | Местные технические требования к конкретным поверхностям, участкам, размерам или конструктивным элементам с областью действия и источниками. Общие требования находятся в `drawing_general.general_requirements`. |
| `relations` | Геометрические связи: соосность, симметрия, касание и другие ограничения номинальной геометрии. |
| `evidence` | Ссылки на страницы и области PDF, исходные надписи и основания выводов. |
| `issues` | Пробелы, неоднозначности, противоречия и нераспознанные обозначения. |
| `readiness` | Раздельные результаты проверки геометрии и полноты технических требований. |

## Отдельный блок общей информации

`drawing_general` передаётся в том же JSON на одном уровне с `surfaces`. Предлагаемый состав блока:

| Поле внутри `drawing_general` | Содержание |
| --- | --- |
| `document` | Идентификатор исходного PDF, редакция и сведения о листах. |
| `part` | Обозначение и наименование детали, материал и другие общие сведения, указанные на чертеже. |
| `units` | Единицы длины, углов и других величин. Требование с собственными единицами, например шероховатость в микрометрах, сохраняет их явно. |
| `standards` | Указанные нормативные документы, редакции и область применения. |
| `general_requirements` | Общие допуски, общая шероховатость, требования к кромкам, покрытиям, термообработке и другие общие указания, если они заданы. |
| `notes` | Остальные общие примечания с исходным текстом, источником и состоянием интерпретации. |

Общие сведения и требования хранятся здесь один раз. В карточке поверхности допустима ссылка на общее требование, но его текст и значения не копируются. Отсутствие такой ссылки не освобождает агент построения от проверки применимых общих указаний.

До построения агент читает `drawing_general`, устанавливает единицы и общие условия, затем определяет применимые к каждому размеру, поверхности или участку общие и местные требования. Для каждого общего требования проверяются область действия и исключения. Местное указание заменяет общее только при установленном правиле исключения для той же характеристики и области; неразрешённое противоречие попадает в `issues`.

Например, общее указание шероховатости Ra 6,3 мкм для поверхностей без отдельного обозначения хранится в `general_requirements`. Местное Ra 1,6 мкм для S001 хранится в `requirements` и связано с S001. Для S001 применяется местное указание, для остальных подходящих поверхностей без отдельного обозначения — общее.

Общие сведения учитываются по назначению: единицы и геометрические указания участвуют в построении формы, материал и требования к изготовлению сохраняются как свойства модели или сопровождающие данные. Допуски и шероховатость сами по себе не изменяют номинальную геометрию. Если смысл общего примечания или его влияние на модель не установлены, оно сохраняется вместе с вопросом в `issues`; его нельзя молча пропустить.

## Что считать поверхностью

Запись в `surfaces` описывает ограниченный участок границы тела: например, торец, стенку отверстия, дно паза, фаску или скругление. Для построения нужны форма, положение, границы и ориентация относительно материала. Одного типа «плоскость» или «цилиндр» недостаточно. Такое разделение геометрии и ограничивающей её топологии соответствует принципу граничного представления в CAD: [Open CASCADE Modeling Data](https://occt3d.com/dev/doc/overview/html/occt_user_guides__modeling_data.html).

Учитываются наружные и внутренние поверхности, переходы и поверхности повторяющихся элементов. Одна поверхность, показанная на нескольких видах, сохраняет один идентификатор. Разные экземпляры одинаковых отверстий имеют разные идентификаторы либо однозначно раскрываемые экземпляры шаблона.

Плоскость условного разреза чертежа сама по себе не становится физической поверхностью детали. Условные изображения, в том числе резьбы, требуют отдельной интерпретации. Для резьб нужно согласовать уровень геометрической детализации и явно указать выбранное представление; условное изображение нельзя незаметно объявить полной геометрией витков.

## Карточка поверхности

| Поле | Содержание |
| --- | --- |
| `id` | Уникальный идентификатор, например `S001`. |
| `body_id` | Тело, которому принадлежит поверхность. |
| `feature_ids` | Связанные конструктивные элементы. |
| `geometry` | Тип, параметры и система координат: плоскость, цилиндр, конус, сфера, тор, поверхность свободной формы и т. п. |
| `boundaries` | Внешние и внутренние контуры, ограничивающие поверхность; ссылки на ориентированные рёбра. |
| `orientation` | Ориентация поверхности относительно материала тела, позволяющая различать наружную стенку и стенку полости. |
| `dimension_ids` | Размеры, определяющие форму, протяжённость и положение. |
| `requirement_bindings` | Ссылки на местные требования непосредственно или через размер; при наличии — ссылки на применимые требования из `drawing_general.general_requirements`, без копирования их содержимого. Для ссылки сохраняется источник: местное или общее указание. |
| `evidence_ids` | Наблюдения этой поверхности на видах и разрезах. |
| `interpretation` | Что прочитано, что вычислено, что предполагается и что остаётся неизвестным, с привязкой к конкретным параметрам. |

Соседство поверхностей определяется общими рёбрами. Если список соседей хранится дополнительно, он проверяется на согласованность с контурами. Параметры свободной формы и сложные границы должны иметь однозначное математическое описание либо оставаться явно неразрешёнными.

## Привязка технических требований

Каждое местное требование хранится один раз в `requirements`, каждое общее — в `drawing_general.general_requirements`. Идентификаторы требований уникальны в пределах всего JSON. Поверхность ссылается на требования через `requirement_bindings`; полный набор применимых требований определяется с обязательным учётом общего блока. Требование к размеру между двумя поверхностями также хранится в одном экземпляре.

Карточка требования содержит:

- `id` и `kind`: идентификатор и категория требования;
- `targets`: поверхности, размеры, конструктивные элементы, тело или ограниченные участки поверхностей, к которым оно относится;
- `specification`: структурированные параметры, значения, единицы, пределы и модификаторы соответствующей категории;
- `raw_text`: исходную запись без потери обозначений; для графического символа также ссылку на его изображение;
- `standard`: обозначение и редакцию нормативного документа, если они установлены;
- `scope`: область действия, исключения и правило применения общего требования;
- `evidence_ids` и `interpretation`: источник, способ получения значения и неразрешённые вопросы.

Если требование относится к участку поверхности, граница этого участка описывается отдельно. Геометрически делить поверхность на несколько граней только из-за различия шероховатости необязательно.

## Размерные допуски и квалитет IT

Квалитет связывается с конкретным размером и его элементом. Это может быть диаметр цилиндрической поверхности или размер между двумя противоположными параллельными поверхностями. Именно такие типы элементов охватывает [ISO 286-1](https://www.iso.org/standard/45975.html). Поэтому единственное поле `it_grade` в карточке каждой поверхности не передаст смысл всех размерных требований.

Для размерного допуска предлагаются поля `designation`, `it_grade`, `fundamental_deviation`, `upper_deviation`, `lower_deviation` и `limit_sizes`. Они заполняются в соответствии с исходной записью и доступными основаниями. Например, в `⌀20 H7` сохраняются номинальный диаметр 20 мм, обозначение H7 и квалитет IT7. Сам по себе IT7 не задаёт положение допуска относительно номинального размера. Предельные отклонения зависят от размера и обозначения; для их получения нужны соответствующие нормативные таблицы: [ISO 286-2](https://www.iso.org/obp/ui/?_escaped_fragment_=iso:std:54915:en).

Численные отклонения, вычисленные по стандарту, помечаются как вычисленные с указанием нормативного источника. Если заданы только численные отклонения, квалитет не подбирается приблизительно. Значение IT может остаться не заданным. Номинал и предельные значения не должны смешиваться при построении геометрии.

## Шероховатость и остальные требования

Для шероховатости сохраняются параметр (`Ra`, `Rz` и другие), значение или пределы, единицы, вид ограничения и дополнительные обозначения, если они заданы: направление неровностей, условия обработки и измерения. Исходный символ сохраняется вместе с интерпретацией. Правила обозначений зависят от применённого стандарта; пример такого стандарта — [ISO 21920-1](https://www.iso.org/standard/72196.html). Нельзя автоматически приписывать его чертежу или заменять Ra на Rz.

Другие категории требований включают допуски формы и расположения, биение, базы и их порядок, покрытия и толщину слоя, твёрдость, термообработку и глубину упрочнения, обработку кромок и прочие текстовые указания. Требование сохраняет свой действительный объект: поверхность, размер, ось элемента, группу поверхностей или всю деталь. Допуск расположения не подменяется геометрическим ограничением идеальной модели.

Общие указания из `drawing_general.general_requirements` распространяются на подходящие поверхности или размеры по правилам раздела «Отдельный блок общей информации». Спорное сочетание указаний отмечается как конфликт, без молчаливого выбора одного значения.

## Неопределённость и готовность результата

Для отдельного параметра различаются прочитанное значение, однозначно вычисленное значение, предположение и неизвестное значение. Для технического требования дополнительно различаются состояния «задано», «не задано после проверки местных и общих указаний», «не удалось прочитать», «неясно, к чему относится» и «не применимо». Пустой список требований сам по себе не означает, что они отсутствуют на чертеже.

Источник включает идентификатор PDF, номер страницы и область с явно указанной системой координат, единицами и поворотом страницы. Одно утверждение может иметь несколько источников; вычисленное значение содержит ссылки на исходные данные и основание расчёта. Неизвестное значение не заменяется нулём.

Для признания геометрии готовой к построению необходимо проверить достаточность параметров и ограничений, согласованность видов и размеров, границы поверхностей, ориентацию, замкнутость оболочек и отсутствие неразрешённых противоречий. Для конструктивной детали проверяется также корректность границ внутренних полостей. Предположение, существенно меняющее форму, должно оставаться блокирующим вопросом до разрешения.

Статус полноты технических требований оценивается отдельно: модель номинальной формы может быть определена, даже когда обозначение шероховатости ещё не прочитано. Проверка готовности включает учёт общих указаний из `drawing_general` и их сочетания с местными требованиями. Такой результат нельзя выдавать за полностью расшифрованный чертёж, пока остаются неразрешённые требования.

JSON Schema проверяет структуру и типы данных. Существование ссылочных идентификаторов, согласованность размеров и корректность геометрии требуют дополнительных проверок. Набор поддерживаемых типов деталей, поверхностей и уровень детализации резьб предстоит согласовать на примерах чертежей.
