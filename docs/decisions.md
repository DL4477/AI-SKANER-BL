# Принятые решения проекта

## Формат передачи данных между агентами

Принято пользователем 8 октября 2026 года. Выбор формата завершён.

Агент чтения и интерпретации PDF-чертежей передаёт результат агенту построения 3D-моделей в формате JSON. Структуру данных и правила их проверки задаёт JSON Schema.

JSON содержит сведения, извлечённые из конкретного чертежа. JSON Schema служит общим контрактом между агентами: определяет поля, типы значений, обязательность и ограничения.

Такой подход позволяет однозначно организовать данные и автоматически проверять их соответствие согласованному контракту. Соответствие схеме само по себе не подтверждает правильность интерпретации чертежа или геометрии.

Конкретные поля, обязательность, ограничения и версия стандарта JSON Schema будут согласованы отдельно. Ранее обсуждавшийся состав данных остаётся предложением; этим решением утверждён формат передачи.

## Охват поверхностей и технических требований

Принято пользователем 8 октября 2026 года.

Итоговый JSON должен содержать сведения обо всех поверхностях детали, необходимые следующему агенту для построения 3D-модели. С поверхностями должны быть связаны заданные для них технические требования, включая квалитет точности IT, шероховатость и другие требования чертежа.

Предлагаемый способ описания геометрии, привязки требований и обработки недостаточных данных изложен в [проекте структуры данных](surface-data-contract.md). Названия полей и правила этой структуры пока обсуждаются.

## Общая информация чертежа

Принято пользователем 8 октября 2026 года.

Общая информация и общие требования чертежа передаются отдельным блоком JSON, отдельно от описаний поверхностей. Агент построения 3D-модели обязан учитывать этот блок вместе с данными поверхностей.

В проекте структуры для этого блока предложено имя `drawing_general`. Общие указания хранятся один раз; их применение к поверхностям и размерам определяется областью действия и указанными исключениями.

## Приложение и подключение модели

Принято пользователем 8 октября 2026 года.

Разрабатывается отдельное приложение для работы с агентом; VS Code используется как среда разработки. Приложение должно поддерживать подключение инструментов агента.

ИИ-модель подключается через API и должна иметь возможность локального развёртывания. Конкретная модель и оборудование для собственного развёртывания пока не утверждены. Кандидаты и устройство приложения описаны в [проекте ядра агента](agent-core-plan.md).

## Основа проектирования приложения

10 октября 2026 года пользователь принял предложенное направление и поручил спланировать проектирование приложения.

Рабочая основа: Python для ядра и обработки документов, FastAPI для связи с интерфейсом, React и TypeScript для интерфейса, Tauri для настольного приложения. Модель работает в отдельном API-сервисе. Kimi K3 остаётся первым кандидатом для испытаний; окончательный выбор модели зависит от проверки на чертежах проекта.

[План проектирования приложения](application-design-plan.md) определяет экраны, границы модулей, хранение и проверку данных, этапы проектирования и порядок последующей реализации. Конкретные поля схемы, область поддержки первой версии и оборудование ещё предстоит определить.

## Первый шаг только интерфейс

10 октября 2026 года пользователь уточнил порядок работы: «начинай постепенно сначала просто интерфейс».

Первым реализуется интерфейс на учебных данных: просмотр чертежа, поверхности и требования, общие сведения, настройки и журнал. Работа модели, проверка данных, исполняемая JSON Schema и экспорт не входят в этот шаг. [Описание первого интерфейса](interface-v01.md).

## Локальный запуск приложения

10 октября 2026 года пользователь уточнил: приложение должно находиться на этом компьютере. Первый интерфейс упаковывается в настольное Windows-приложение Tauri с установщиком и ярлыком. Для его обычного запуска не требуются браузер, VS Code или сервер разработки. Это уточнение не добавляет подключение модели или ядро агента в текущий этап.

## Первое подключение модели

10 октября 2026 года пользователь выбрал внешний API Kimi и поручил реализовать инфраструктуру подключения. В версии 0.2 подключается `kimi-k3` через `https://api.moonshot.ai/v1`. Локальный сервер модели и другие поставщики остаются следующими расширениями; качество Kimi на производственных чертежах ещё предстоит проверить.

Для этого небольшого этапа сетевой клиент и защищённое хранение ключа реализуются в уже существующем процессе Tauri на Rust. Это позволяет проверять API без дополнительного сервера и упаковки Python. Python остаётся рабочим направлением для обработки документов и управляющего ядра; его границу с Rust предстоит определить при подключении инструментов. FastAPI и отдельный Python-процесс пока не реализованы.

Ключ сохраняется в Windows Credential Manager и не возвращается интерфейсу при чтении настроек. Запросы выполняются только вручную. Четыре проверки используют учебные данные: список моделей, текст, изображение и JSON по тестовой схеме. Успешная проверка не подтверждает качество разбора чертежей, поддержку инструментов или полноту описания поверхностей. [Подробности реализации](model-connection.md).
